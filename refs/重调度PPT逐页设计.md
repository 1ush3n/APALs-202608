### 讲稿

> 各位老师好，我今天汇报的是飞机脉动装配线中，针对工序延迟开始的预测-反应式重调度方法。
>
> 问题的背景是：我们有一个已经优化好的初始排程方案。但在实际执行过程中，比如执行到总工期的 15% 到 65% 之间的某个时刻，部分工序因为物料没到齐、或者设备临时故障，无法按原计划的时间开工。
>
> 这时候我们面临一个两难：已经开工的任务不能动——工人已经在现场了、站位也已经绑定了；但剩余的任务必须重新排。我们希望重排的结果既不要超期太多，也尽量少改动原来的方案，因为工厂现场最怕频繁换站位换人。
>
> 右边这张时间轴展示了重调度的基本模型：t₀ 是重调度触发时刻，之前的任务是冻结的，之后的任务可以移动，其中标注红色的就是被延迟的问题工序。

### 关键公式

\[
t_0 \sim \text{Uniform}(0.15 \cdot T_{\text{takt}},\; 0.65 \cdot T_{\text{takt}})
\]

### 讲稿

> 这是我们的整体技术架构。整个系统是一个以 PPO 强化学习为核心、以初始调度方案为引导的闭环。
>
> 流程从左到右：第一步，我们有一个已经训练好的初始调度模型，它生成的方案作为 Baseline，makespan 大约 130 小时。第二步，场景生成器随机采样一个重调度起始时刻，并挑选一部分尚未开工的任务，给它们注入延迟——也就是推迟它们的物料释放时间。第三步，重调度环境拿到这个场景后，把已经开工的任务冻结恢复，同时把 Baseline 的信息编码成 6 个额外的特征维度，喂给图神经网络。第四步，PPO Agent 在这个环境中进行微调式训练，同时优化三个目标。第五步，每次评估时，我们对输出的调度方案进行 10 维硬约束全量审计，并计算一个复合评分。
>
> 三个关键创新我标注在底部：一是 6 维 Baseline 引导特征让网络知道"原来是怎么排的"，二是奖励函数同时考虑了节拍超期和稳定性偏离，三是我们实现了全自动的约束合规性诊断。

### 讲稿

> 第三页讲场景是怎么生成的。这是一个三步随机化流程。
>
> 第一步，确定重调度发生的时刻 t₀。它在总工期的 15% 到 65% 之间均匀采样——为什么要设这个范围？因为如果太早发生，大部分任务还没开工，那就跟从头排没有区别；如果太晚发生，大部分任务都已经做完了，重调度的意义就不大。
>
> 第二步，遍历 baseline 中所有在 t₀ 之后才开工的任务，以 15% 的概率标记为"被延迟"。这意味着大约 22 个任务会出问题，其余 123 个任务正常。
>
> 第三步，被标记的任务，它的物料释放时间被推迟到"原计划开工时间"和"t₀ 加一个 5 到 50 小时的随机延迟"中的较大值。保证延迟只会推后不会提前。
>
> 底下说明我们支持三种场景来源：代码注入用于单元测试、CSV 文件用于固定复现某个特定场景、随机采样是训练和评估的主力方式。评估时种子固定为 30300 系列，确保同一个 episode 的评估结果完全可复现。

### 讲稿

> 第四页讲的是最核心的状态恢复机制。当我们把场景注入到环境里时，环境需要"快进"到 t₀ 时刻，并且完整恢复那些已经发生的事情。
>
> 左边是六步恢复流程。第一步，把所有状态变量清零。第二步，把延迟任务的释放时间写进去，这样 ActionMasker 就会自动在释放时间之前把它们屏蔽掉。第三步，遍历 baseline 找出所有 start ≤ t₀ 的任务。第四步是最关键的——对每个冻结任务，我们不仅要标记它的 status 为"已完成"，还要恢复它对环境的全部副作用：站位的负载累加、站位的 wall-clock 时间推进、工人的释放时间更新，以及最关键的——工人与站位的终身绑定关系。第五步，对于已经到结束时间的冻结任务，我们需要手动触发它的工艺后继解锁。第六步，计算理论下界，判断在当前约束下是否还有可能在节拍内完成。
>
> 右边上方的图展示了工人绑定的物理含义：在 APAL 脉动装配线中，工人一旦进入某个站位，就被"锁"在那里，不能再跨站流转。这是我们这个调度问题最特殊的约束。右边的公式是下界估计：取三个下界中的最大值。如果这个下界已经超过了 130 小时的节拍，系统就会自动把稳定性惩罚的权重降到 0.35，告诉模型"不要硬跟 baseline 了，先想办法完工"。

### 排版布局

  │23 │延误  │ (now-base.start)/T        │ "已经耽误了多少"   │
  │   │比率  │ if overdue & not done     │ 加速补救决策       │
  └───┴──────┴──────────────────────────┴─────────────────┘

  ┌───────────────────────────────────────────────────────┐
  │  💡 设计洞察                                           │
  │                                                       │
  │  · 所有值除以 Takt 做归一化 → 跨数据集尺度不变             │
  │  · [18] 负值时网络会意识到"这个任务早就该开始了"             │
  │  · [21][22] 是二值 flag，给网络最明确的硬约束信号           │
  │  · [23] 随时间动态增长 → 形成"越来越紧迫"的梯度信号         │
  └───────────────────────────────────────────────────────┘
```

### 讲稿

> 第五页讲的是我们最核心的一个设计——Baseline 引导特征。
>
> 重调度和从头排程最大的区别在于，我们有一个已知的初始方案作为参考。如果把这个参考信息直接编码进神经网络的输入中，模型就不需要从零开始"猜测"原来是怎么排的，而是可以在这个基础上做微调。
>
> 所以我们把 Task 节点的输入从 18 维扩展到了 24 维，新增的 6 个维度都在这个表里。每一行是一个特征，我挑重点说：第 18 维是"距离 baseline 计划开工时间还有多久"——如果这个值变成负数了，说明计划时间已经过了但任务还没开工，网络就会感知到紧迫感。第 19 和第 20 维是 baseline 的站位和团队参考——如果模型选了和 baseline 一样的站位和团队，就不会触发稳定性惩罚；但这不是硬约束，模型仍然可以根据实际情况选择不同方案。第 21 和第 22 是硬标记——冻结和延迟，给网络最明确的信号。第 23 维是我们最新加的"延误比例"——如果当前时间已经超过了 baseline 的开工时间但任务还没完成，这个值就会从 0 开始随时间增长，形成一个越来越强的补救信号。
>
> 底下补充一句设计哲学：所有特征都除以了节拍时间做归一化，保证在 283 个任务的小图和 3182 个任务的大图上，数值范围是一致的。

  ┌─────────── 上半部分：每步基础奖励 ───────────────────┐
  │                                                      │
  │   Step Reward（与标准 PPO 一致，每步注入）              │
  │                                                      │
  │   r_step = -(ΔMakespan / M_ideal) · 100       ①    │
  │            -(ΔBalance / L_ideal) · 50          ②    │
  │            + critical_bonus                    ③    │
  │                                                      │
  │   最终 r_step ← clip(r_step, -50, +50) × 0.005      │
  └──────────────────────────────────────────────────────┘

  ┌─────────── 下半部分：终局结算（Episode 结束时一次性注入） ─┐
  │                                                        │
  │   ┌──────────────────────────────────────────────┐     │
  │   │              终局奖励结构                       │     │
  │   │                                              │     │
  │   │  r_terminal = -(Takt_Pen + Stability_Pen)    │     │
  │   │                                              │     │
  │   │  ┌─────────────────────────────────────┐     │     │
  │   │  │ 节拍超期惩罚                          │     │     │
  │   │  │ Takt_Pen = max(0, M - T) / T · 1.0  │     │     │
  │   │  │                                       │     │     │
  │   │  │ M=140h, T=130h → Pen = 0.077        │     │     │
  │   │  └─────────────────────────────────────┘     │     │
  │   │  ┌─────────────────────────────────────┐     │     │
  │   │  │ 稳定性惩罚 = α · (开工偏离+站位变更+  │     │     │
  │   │  │             团队变更)                 │     │     │
  │   │  │                                       │     │     │
  │   │  │ α = 1.0 (节拍可达)                    │     │     │
  │   │  │ α = 0.35 (不可达 → 放松跟随)          │     │     │
  │   │  └─────────────────────────────────────┘     │     │
  │   └──────────────────────────────────────────────┘     │
  └────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────┐
  │  ⚠️ 已知局限：终局惩罚仅通过 GAE（γ=0.999, λ=0.9）      │
  │     反向传播约 30 步有效 → 前半段行为缺乏稳定性指导        │
  └────────────────────────────────────────────────────────┘
```

### 讲稿

> 这一页讲奖励函数。我们把它分成两部分：每步奖励和终局结算。
>
> 每步奖励和我们标准训练一样，就是 makespan 增量惩罚加上负载均衡惩罚，再加一个可选的 CPM 关键路径奖励。这部分保证模型在每一步都在追求"快"和"均衡"。
>
> 重点是终局结算。当所有任务都完成之后，我们注入两项额外的惩罚。第一项是节拍超期惩罚——如果你比 baseline 的 130 小时多用了 10 小时，惩罚就是 10/130 约等于 0.077。第二项是稳定性惩罚，包含三个子项：开工时间偏离 baseline 的程度、站位的变更率、团队的变更率。这三个子项分别乘以 0.20、0.10、0.05 的权重，再加权求和。
>
> 有一个重要的自适应机制：如果理论下界显示在当前约束下已经不可能在节拍内完成了，系统会自动把稳定性权重降到 0.35，告诉模型"别太拘泥于 baseline 了，先干活"。
>
> 底下标注了一个已知局限：这两项终局惩罚只在 episode 的最后一步注入，通过 GAE 反向传播，由于衰减，只有最后约 30 步的行为能有效接收到这个信号。这是我们在后续优化中需要解决的核心问题。

### 讲稿

> 最后一页做一个坦诚的分析和展望。
>
> 上面三个根因卡片一一对应我们的三个核心问题。根因一是最致命的：我们的节拍和稳定性惩罚只在整个 episode 结束的时候注入一次，但一个 episode 通常有两百多步。通过 GAE 的反向传播，因为有两个 0.9 的衰减因子连乘，到第 150 步的时候信号的权重已经衰减到原来的 10⁻¹⁰ 量级。这意味着模型在 episode 的前 75% 的时间里，根本不知道"要靠近 baseline"这件事。它只是在按初始训练的本能最小化 makespan。
>
> 根因二是新特征的冷启动——那 6 列 baseline 特征的权重从零开始学，即使我们调大了学习率，对于 300 个 episode 来说还是偏慢。根因三是数据层面——只有 15% 的任务被延迟，大部分场景的信号太稀疏。
>
> 下面是我们已经做的和计划做的优化。P0 是每步注入微量的稳定性信号，这是最重要的一个改动——在每一步如果模型选了 baseline 同意的站位，就给一个很小的正奖励。这样全 episode 都有梯度指导。P1 是对那 6 列新特征用更高的学习率，加速它们长大。P2 我们已经完成了——扩大的扰动强度和新的延误比特征。下面三个是中长期方向：工人锁释放让模型在更大的动作空间里学习、多扰动联合训练提升鲁棒性、端到端联合训练把初始调度和重调度融合成一个模型。
>
> 总结一下：我们的重调度系统已经实现了完整的闭环——从场景生成到约束诊断。方案合法、有提升趋势，但提升幅度受限于 GAE 终局信号衰减。P0 的改进正在实施中，预期能将 makespan 进一步缩小 2 到 3 小时。
>
> 谢谢各位老师，请批评指正。

\[
\text{GAE 权重衰减: } (\gamma \lambda)^{k} = (0.999 \times 0.9)^{k} \approx 0.9^{k}
\]

\[
\text{第 1 步信号强度: } 0.9^{200} \approx 7 \times 10^{-10} \quad \text{(完全消失)}

## 附录：PPT 整体风格建议

| 要素 | 建议 |
|:---|------|
| **主色调** | 深蓝 `#1A3A5C`（标题/重点）+ 浅灰 `#F5F6FA`（背景）+ 白 `#FFF`（卡片） |
| **强调色** | 绿 `#27AE60`（通过/正面）、红 `#C0392B`（问题/超期）、橙 `#E67E22`（高亮/警告） |

| **动画** | 每页最多 1-2 个淡入动画，不要逐条飞入（听众会烦） |
| **公式** | 用 PowerPoint 公式编辑器（`Alt+=`），不要截图 |
| **表格** | 表头深蓝底白字，数据行交替浅灰/白色，最大 8 行 |
| **卡片** | 圆角矩形 + 轻微阴影（右下偏移 3px, 透明度 20%），每页不超过 3 个卡片 |
| **代码** | 仅在必须展示 API 时使用，用深色底 + Consolas，行数 ≤ 8 |
