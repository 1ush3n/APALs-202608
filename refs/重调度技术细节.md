## 1. 系统架构总览

### 1.1 设计理念

预测-反应式重调度（Predictive-Reactive Rescheduling）系统的核心思想是：**在生产执行过程中，当部分工序因延迟无法按原计划开工时，在尊重已开工（冻结）任务的前提下，对剩余任务进行重新排程，追求最小化完工时间偏离和方案稳定性。**

系统采用 **强化学习（PPO）+ 初始调度引导** 的双层架构：

```

│                    重调度系统架构                          │

│  │ 初始调度模型  │    │ Baseline 调度 │    │ 延迟场景   │ │
```

```python
@dataclass(frozen=True)
```

从 `results/final_schedule.csv` 加载（由初始调度模型在确定性贪婪模式下生成）。CSV 格式：

| TaskID | StationID | Team | Start | End | Duration |
|--------|-----------|------|-------|-----|----------|
| 0 | 3 | [0, 5, 12] | 0.0 | 8.5 | 8.5 |

**节拍时间（Takt Time）** 定义为 `BaselineSchedule.makespan`，是初始调度方案的总完工时间，也是重调度的"按时完成"目标线。

### 2.3 RescheduleScenario（重调度场景）

[`reschedule.py` L30-33](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/utils/reschedule.py#L30-L33)

```python
@dataclass(frozen=True)
class RescheduleScenario:
    start_time: float                           # 重调度起始时刻（小时）

```

- `start_time`：生产执行到此刻触发重调度，此时刻之前已开工的任务被冻结

## 3. 重调度场景生成

### 3.1 采样策略

[`_build_reschedule_scenario()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L219-L232) 支持三种场景源（优先级递减）：

1. **代码注入**（测试用）：`env._forced_reschedule_scenario` 直接赋值
2. **CSV/YAML 文件**：通过 `reschedule_scenario_path` 加载固定场景
3. **随机采样**（训练/评估用）：调用 `sample_task_delay_scenario()`

### 3.2 随机延迟场景生成算法

[`sample_task_delay_scenario()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/utils/reschedule.py#L190-L213) 的数学模型：

**Step 1 — 确定重调度起始时刻**：

\[
\text{start\_time} \sim \text{Uniform}(takt \times r_{\min}, takt \times r_{\max})
\]

其中 \(r_{\min} = 0.15\)，\(r_{\max} = 0.65\)（可配置）。

**Step 2 — 选择被延迟的任务**：

对每个 `task ∈ baseline.tasks`，若 `task.start > start_time`（尚未开工），以概率 `task_prob = 0.15` 将其标记为延迟任务。

**Step 3 — 计算新释放时间**：

\[
\text{release\_time} = \max\bigl(task.start,\; start\_time + \text{Uniform}(5.0,\; 50.0)\bigr)
\]

该公式保证：延迟后的释放时间不早于原始开工时间（即延迟只可能推后，不可能提前）。

**Step 4 — 返回场景**：

```python
return RescheduleScenario(
    start_time=start_time,
    task_release_times={tid: release_time for delayed tasks}
)
```

### 3.3 场景的评估随机种子

在 [`evaluate_reschedule_model()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/train.py#L677) 中评估固定使用 `seed = 30300 + i`（`i` 为评估轮次索引），保证不同 Episode 间评估的可复现性。

## 4. 冻结任务植入与约束恢复

### 4.1 全流程

[`_apply_reschedule_scenario()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L233-L303) 在 `reset()` 中被调用（仅当 `enable_reschedule_mode=True`），执行以下步骤：

```
1. 清空环境状态变量（task_status, worker_free_time, events, ...）
2. 注入延迟任务的释放时间 → task_material_ready + MATERIAL_ARRIVE 事件
3. 遍历 baseline.tasks，识别已开工任务（start ≤ start_time）
4. 对每个已开工任务：
   - task_status = 2（已完成/已调度）
   - 恢复其 station_id、team、start、end
   - 恢复各站位的 activity load 和 wall_clock
   - 恢复工人 free_time 和站位绑定（worker_locks）
   - 如果 end > current_time，推入 TASK_FINISH 事件
   - 否则，对 successor 完成 completed_preds++ 以解锁后继
5. 重新扫描所有 task_status=0 的任务，若 completed_preds == num_preds 则设为 ready (1)
6. 计算重调度下界 (reschedule_lower_bound) 和节拍可行性 (reschedule_takt_feasible)
```

### 4.2 工人站位绑定的严格恢复

[environment.py L275-280](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L275-L280)：

```python
for w in team:
    self.worker_free_time[w] = max(self.worker_free_time[w], end)
    if sid >= 0 and self.worker_locks[w] == 0:
        self.worker_locks[w] = sid + 1
```

工人一旦被分配到某站位，其 `worker_locks` 绑定为 `station_id + 1`（1-based），此后**只能在该站位执行任务**。这是 APAL 的核心物理约束——跨站流转需释放后重新绑定，但在当前简化模型中绑定终生有效。

### 4.3 物料释放时间约束

[environment.py L251-255](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L251-L255)：延迟任务的释放时间通过 `task_material_ready` 存储，并通过 `MATERIAL_ARRIVE` 事件触发。`ActionMasker` 在生成掩码时会检查 `task_material_ready[t] > current_time` 来排除不可调度的任务。

验证逻辑在 [`_validate_worker_team()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L830-L836) 中作为硬拒绝条件：

```python
if hasattr(self, 'task_material_ready') and self.task_material_ready[task_id] > self.current_time + 1e-9:
    return {'reason': 'task_release_time_not_reached', ...}
```

### 4.4 下界估计

[`calculate_reschedule_lower_bound()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/utils/reschedule.py#L216-L232) 计算三重下界的最大值：

\[
LB = \max\left(
\underbrace{\max_{task.start \leq t} task.end}_{\text{冻结任务最晚完工}},
\;\;
\underbrace{t + \frac{\sum_{i \in \text{remaining}} d_i}{|S| \times slots}}_{\text{剩余工作量/总槽位}},
\;\;
\underbrace{\max_{i \in \text{remaining}} release_i}_{\text{最晚释放时间}}
\right)
\]

若 \(LB > takt\)，则 `reschedule_takt_feasible = False`，稳定性惩罚权重自动放松（乘以 `reschedule_infeasible_stability_relax = 0.35`）。

## 5. Baseline 引导特征编码

重调度模式下，每个 Task 节点的输入特征从 18 维扩展到 **24 维**（列 18-23 为 Baseline 引导特征）。

### 5.1 特征定义表

| 维度 | 名称 | 计算公式 | 含义 |
|:---:|------|----------|------|
| **18** | `baseline_start_delta` | `(baseline.start - current_time) / takt` | 距 baseline 计划开工时间的相对偏移（负 = 已过时） |
| **19** | `baseline_station_norm` | `(baseline.station_id + 1) / num_stations` | baseline 分配的站位（归一化） |
| **20** | `baseline_team_size_norm` | `len(baseline.team) / num_workers` | baseline 分配的团队规模（归一化） |
| **21** | `is_frozen` | `1.0 if baseline.start ≤ start_time else 0.0` | 是否为冻结任务（重调度前已开工） |
| **22** | `is_delayed` | `1.0 if release_time > start_time else 0.0` | 是否被延迟（物料不可用） |
| **23** | `delay_ratio` | `(current_time - baseline.start) / takt` if overdue & not done | 已延误时长占节拍的比例 |

### 5.2 特征写入位置

特征通过 [`_fill_reschedule_task_features()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L1198-L1219) 在以下三处调用：

1. **`_get_observation()`** — 每步实时观测
2. **`environment.py` 的 `rebuild_state_from_snapshot()`** — CPU 端快照重建
3. **`utils/vector_env.py` 的 `EnvProxy.rebuild_state_from_snapshot()`** — Vector Env 代理端重建
4. **`utils/gpu_graph_manager.py` 的 `batched_rebuild_on_gpu()`** — GPU 批量图原地覆写

```python
# GPU 批量重建中的向量化写入（gpu_graph_manager.py L222-225）
delay_mask = (flat_current_times_t > flat_base_start + 1e-9) & (flat_status != 2)
batch_template['task'].x[:, 23] = (
    (flat_current_times_t - flat_base_start) / torch.clamp(flat_base_makespan, min=1e-6)
) * delay_mask.float()
```

### 5.3 设计意图

- **[18] 相对偏移**：让网络感知"这个任务按原始计划是早该开始了还是还很远"，指导调度优先级
- **[19][20] 站位/团队参考**：提供"初始方案是怎么排的"的软参考，降低稳定性惩罚
- **[21] 冻结标记**：让网络明确知道哪些任务不可改
- **[22] 延迟标记**：让网络定位问题任务
- **[23] 延误比**：让网络感知"已经耽误了多少"，引导加速补救

## 6. 重调度奖励函数设计

### 6.1 每步基础奖励

与环境本身相同的 makespan 增量惩罚 + 负载均衡惩罚：

```python
# environment.py L972-991
norm_delta_makespan = (delta_makespan / ideal_makespan) * 100.0
norm_delta_std = (delta_std / ideal_station_load) * 100.0
base_penalty = -(r_coef_makespan * norm_delta_makespan) - (r_coef_std * norm_delta_std)
```

通过 `ideal_makespan` 和 `ideal_station_load` 归一化实现**尺度不变性**。

### 6.2 终局结算——节拍与稳定性惩罚

[environment.py L1017-L1043](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/environment.py#L1017-L1043)：

当 Episode 终止（所有任务完成）时注入四项惩罚：

#### a) 节拍超期惩罚

\[
\text{takt\_pen} = w_{\text{takt}} \cdot \frac{\max(0,\; makespan - takt)}{takt}
\]

其中 \(w_{\text{takt}} = 1.0\)，直接以节拍比例为尺度衡量超期程度。

#### b) 开工时间稳定性惩罚

\[
\text{start\_pen} = w_{\text{start}} \cdot \frac{1}{|\text{movable}|} \sum_{i \in \text{movable}} \frac{|start_i - baseline.start_i|}{takt}
\]

\(w_{\text{start}} = 0.20\)，衡量所有可移动任务的开工时间偏离 baseline 的平均程度。

#### c) 站位变更率惩罚

\[
\text{station\_pen} = w_{\text{station}} \cdot \frac{\#\{i: station_i \neq baseline.station_i\}}{|\text{movable}|}
\]

\(w_{\text{station}} = 0.10\)，越低越好（越"尊重"初始方案的站位布局）。

#### d) 团队变更率惩罚

\[
\text{team\_pen} = w_{\text{team}} \cdot \frac{\#\{i: team_i \neq baseline.team_i\}}{|\text{movable}|}
\]

\(w_{\text{team}} = 0.05\)，鼓励保持原班人马。

#### 综合公式

\[
\text{stability\_penalty} = \alpha \cdot (\text{start\_pen} + \text{station\_pen} + \text{team\_pen})
\]

其中 \(\alpha\) 为可行性放松因子：

\[
\alpha = \begin{cases}
1.0 & \text{if } LB \leq takt \text{ (节拍可达)} \\
0.35 & \text{if } LB > takt \text{ (不可能在节拍内完成，放松对 baseline 的跟随)}
\end{cases}
\]

#### 注入到累积奖励

```python
reward -= (takt_pen + stability_penalty) * reward_scale * 100.0
```

### 6.3 奖励信号传播

终局惩罚通过 GAE（\(\gamma=0.999,\ \lambda=0.9\)）反向传播：

- Episode 最后 ~30 步能收到有效梯度（\(0.9^{30} \approx 0.04\)）
- 前半段动作因衰减过深，几乎无法感知终局信号 → **这是当前性能提升不显著的主要原因，后续优化见 §12.1**

## 7. 约束违规诊断与复合评分

### 7.1 十维硬约束检查

[`_compute_reschedule_constraint_metrics()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/train.py#L605-L764) 对每个评估场景的输出方案进行全量约束审计：

| 约束 | 检验逻辑 | 违规后果 |
|------|---------|:---:|
| `frozen_violation_count` | 冻结任务的 (station, team, start, end) 必须与 baseline 完全一致 | 方案不可行 |
| `release_violation_count` | 延迟任务的实际开工时间 ≥ `task_material_ready` | 方案不可行 |
| `precedence_violation_count` | 对每条工艺优先边 (src, dst)，`pred.end ≤ succ.start` | 方案不可行 |
| `worker_overlap_violation_count` | 同一工人在两条任务的 [start, end) 区间不能有交集 | 方案不可行 |
| `station_slot_violation_count` | 任一时刻每个站位的并发任务 ≤ `max_slots_per_station` | 方案不可行 |
| `skill_violation_count` | 工人的技能矩阵对应维度必须 > 0.5 | 方案不可行 |
| `demand_violation_count` | 实际派工人数 ≥ 工序需求人数 | 方案不可行 |
| `duplicate_task_count` | 同一 `task_id` 不能出现两次 | 方案不可行 |
| `missing_task_count` | 完成的任务数必须等于总任务数 | 方案不可行 |
| `invalid_step_count` | 推理过程中是否出现非法动作 | 推理错误 |

### 7.2 复合评分

[`calculate_reschedule_composite_score()`](file:///d:/OneDrive/研究生/HGP-期刊/Dynamic_APAL_RL_v2-重构版/utils/reschedule.py#L260-L295) 将多目标加权为单一标量：

```python
score = sum([
    makespan / takt,                                  # 完工时间
    r_coef_std * balance_std / ideal_load,             # 负载均衡
    w_takt * takt_violation / takt,                    # 节拍超期
    w_start * start_deviation / takt,                  # 开工偏离
    w_station * station_change_rate,                   # 站位变更
    w_team   * team_change_rate,                       # 团队变更
])
```

`selection_score = score if eligible else 1e9 + score`，确保不可行方案永远不会当选最佳。

## 12. 后续优化方向

### 12.1 核心瓶颈：终局奖励的 GAE 衰减

当前设计将节拍与稳定性惩罚全部在 Terminal 一次性注入，而 Episode 约 200 步，GAE 反向传播使得前 150 步的梯度衰减到原始信号的 <1%。这导致智能体在 episode 前半段完全按照初始调度本能行事，无法感知"靠近 baseline"的需求。

**改进方向**（已在根因分析中详述）：在每步动作中注入微量即时稳定性引导信号（如 station 匹配奖励），使全 Episode 都有梯度指导。

### 12.2 交替训练策略

当前重调度训练仅在 `data/283.csv` 单一数据集上进行。可以将 `train_data_path_or_dir` 指向多数据集目录实现多图交替训练，提升泛化能力。

### 12.3 工人重分配机制

当前实现中，工人一旦在 frozen 任务中被绑定到某站位（`worker_locks = station_id + 1`），终生无法改变。实际场景中，工人完成当前任务后应当可以在不同站位间重新分配。这需要实现 **锁释放** 机制。

### 12.4 多扰动类型扩展

当前仅支持工序延迟开始场景。可扩展至：
- 工人缺勤 → 已有事件引擎支持（`WORKER_LEAVE/RETURN`），需与重调度联合
- 站位故障 → 已有 `STATION_BREAKDOWN/RECOVER` 事件，需集成
- 急件插入 → 需新任务动态添加到环境中

### 12.5 端到端联合训练

当前采用"先训练初始调度 → 固定 → warm-start 重调度"的两阶段范式。可探索**联合训练**：每 Episode 的前半段 run 初始调度，后半段触发延迟并切换 rewards 权重，让一个模型同时学会最优初始方案和鲁棒重调度。

### 12.6 不确定性感知

引入贝叶斯神经网络或 Ensemble 方法估计每个动作的不确定性，使重调度策略在面对未见过的扰动类型时更加鲁棒。
